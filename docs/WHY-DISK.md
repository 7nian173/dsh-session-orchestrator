# 为什么值这个代价 · 测量与依据

这份文件回答一个问题：**插件在你（和对方）的工作区里建目录、写文件，这个越权行为换来了什么？**

❓ **先说清楚可信度**：下面的数字来自**本插件开发过程 + 若干小型协作任务**的实测，
样本量小、配置单一。换模型、换 provider、换任务类型都会变。
**请以自己使用为准**，不要拿这里的数字去套你的场景。

---

## 一、本体量

| 项 | 数 |
|---|---|
| 唯一信件数 | 259 封 |
| 正文总字数 | 250,944 字 |
| 信封文件数 | 405 份（双侧各一份副本） |
| 去重后正文总量 | 250,944 字（约 40 万 token 单次） |

> 为什么要去重：一封信在发信方和收信方的工作区各存一份 `.md`，
> 但正文只被写一次、通常只被读一次。按 405 份直接算会重复计一遍。

---

## 二、两种消耗分开算

按你关心的口径，一封信的成本分三层：

| 层 | 内容 | 估算 |
|---|---|---|
| **正文生成** | agent 写这封信（output） | 约 40 万 token |
| **正文阅读** | 对方打开信封读（input） | 约 40 万 token |
| **运载层** | 通知索引 + 开工横幅 + 工具返回值 | 约 12 万 token |
| **合计** | | **约 92 万 token** |

### 结构占比

```
正文生成  43%
正文阅读  43%
运载层    13%
```

**这个结构决定了优化方向**：能省的是「少写信、写短些」，不是「压缩通知」。
通知层只占 13%，压到零也只省 13%。

---

## 三、和「不走磁盘」的对比

如果**不**建目录，就得把正文直接推进对方对话。同一个任务量下：

| | 走磁盘（本插件） | 不走磁盘（直接推送） |
|---|---|---|
| 正文什么时候进上下文 | **对方决定** | 强制，立即 |
| 一次 3000 字信的即时成本 | 约 130 token（索引） | 约 5000 token（全文） |
| 对方正在忙时 | 排队，不打断 | **打断** |
| 被压了怎么办 | 落盘可查，可重开 | 翻聊天记录 |
| 同一封信被两个会话引用 | 磁盘一份 | 各推一次，**重复付费** |

**最关键的一条是「对方决定」**：正文落盘之后，对方只有在**真的需要**时才读。
如果它看索引就够（比如只是一条进度通知），那 3000 字一个字都不用花。

而在「直接推送」模型里，**发信方替收信方决定了要花这笔钱**。

## 四、这套设计依赖什么（以及它什么时候不成立）

### 依赖

1. **KV cache 的前缀匹配**：注入发生在上下文**末尾**，已有前缀不变，缓存仍有效。
   → 如果把通知插进系统提示中间，后面全部失效，代价远大于通知本身。
   依据：[Don't Break the Cache (arXiv:2601.06007)](https://arxiv.org/html/2601.06007v2)
   —— 该文实测「把动态内容放在系统提示末尾」比「朴素全上下文缓存」更稳定。

2. **provider 提供自动 prompt caching**：
   论文实测各家 41-80% 成本下降、TTFT 13-31% 改善。

3. **正文可以按需读**：对方有能力自己判断「要不要打开」。

### 什么时候不成立

| 情况 | 会怎样 |
|---|---|
| provider **不支持** prompt caching | 「注入在末尾」的优势消失，但仍比推送全文便宜 |
| 信**总是很短**（一两百字） | 磁盘机制的收益下降，直接推送可能更简单 |
| 对方**每次都全文读** | 那磁盘只省了「不打断」，没省 token |
| 网络/磁盘慢到写入成为瓶颈 | 落盘开销会超过收益（本项目未见） |

## 五、这些数字是怎么得出的

| 数 | 来源 |
|---|---|
| 信件数、正文字数 | 直接读 `.dsh-mail/_letters.json` 的 `body` 字段 |
| 信封份数 | 数 `envelope/` 目录下的 `.md` |
| token 估算 | 中英混排技术文档按 **1.6 token/字**（保守取值） |
| 运载层估算 | 通知约 130 token × 投递次数；横幅约 65 token × 回合数；工具返回约 150 token × 调用次数 |
| cache 表现 | 读 DSH `cost-meter` 账本（`input` / `cacheRead` / `cacheWrite`） |

### 已知的误差来源

1. **token 换算是估的**，不是分词器算的。中文、代码、路径的实际比例差别可达 ±30%。
2. **「投递次数」和「回合数」是估计的**，账本不记录横幅注入了几次。
3. **无法归因的部分**：一次通知注入如果导致缓存重建，那部分成本记在总量里，
   但**分不出是不是插件引起的**。所以本文只报「插件直接消耗」，不报「插件引发的间接消耗」。

---

## 六、结论

**这个插件的开销可以忽略**（在本文测过的配置下）。

它真正的价值不是「省 token」，而是**把「花多少 token」的决定权从发信方交给了收信方**。

代价是它必须在你和对方的工作区里建目录——这是有意的越权，
也是这套机制唯一能落地的方式。
