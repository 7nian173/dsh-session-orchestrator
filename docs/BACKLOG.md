# 待办与改进方案

记录已知问题、已验证的缺陷和待定的设计改进。每条都写清现象、影响、方案与风险，不写"以后再看"。

状态取值：`待修` / `方案待定` / `观察中` / `已修`。

## 1 好友表按名字做全局键，跨工作区同名会话互相覆盖

状态：**待修**（缺陷，已在实盘触发）

**现象**。同一个 DSH 实例里，不同工作区的会话在 `friends.json` 里以名字为唯一键。两个工作区各有一个叫 `lead` 的会话时，后注册的把前一个覆盖掉，前一个再发信就报 `SENDER_NOT_REGISTERED`。

实测：工作区 A 的 `lead` 覆盖掉工作区 B 的 `lead`，后者发信失败，只好改名才恢复。

**影响**。多项目共用一个实例时必然踩，且失败发生在发信那一刻，看起来像插件坏了。

**方案候选**。

| 方案 | 做法 | 代价 |
|---|---|---|
| A 名字加工作区前缀 | 注册时默认 `工作区简称-名字` | 破坏现有名字的可读性，迁移要处理已有条目 |
| B 键改成 `(工作区, 名字)` | 表结构升 v2，查找按调用方工作区 | 要写迁移；跨工作区查找规则要重新定义 |
| C 冲突时自动加后缀 | 撞名就 `lead-2` | 治标，用户记不住到底是哪个 |

倾向 B，配一条迁移：旧表读入时按 `sessionId` 反查 cwd 补齐工作区字段。

## 2 自动化流程被人工审批打断

状态：**方案待定**（设计改进）

**现象**。插件驱动的自动化部署走到需要授权的工具时，必须有人点同意，流程停在那里等。对"让 agent 自己跑完"的场景这是硬阻断。

**宿主提供的接口**（已核实契约）。

```
approval/request  waterfall  (req, next) => Promise<ApprovalOutcome>
req: { agent, toolName, callId?, reason?, displayReason?, signal? }
ApprovalOutcome: 'allowed-once' | 'rejected' | 'cancelled' | 'unavailable'
```

事件是 scope-filtered 的，agent 级别的监听只收该 agent 的请求。插件返回一个 outcome 即claim 该请求，返回 `next()` 则交给下一个应答者。

**一个关键限制**。`req` 里**没有工具参数**，只有 `toolName`。所以自动放行只能按"哪个工具"判断，判断不了"哪条命令"。放行 `bash` 就等于在该窗口内放行任意 bash 命令。

**方案候选**。

| 方案 | 做法 | 风险 |
|---|---|---|
| A 一次性授权 | 用户把权限档位调高，整段任务不再逐次询问 | 粗粒度，覆盖全程，无法追责到具体调用 |
| B 插件端自动审核窗口 | 插件订阅 `approval/request`，窗口期内只对白名单工具回 `allowed-once`，其余交给人；窗口随任务自动开关，每次放行写留痕 | 本质是绕过人工闸门，白名单错一次就是事故 |
| C 跳转让用户手点 | 维持现状，遇到授权就跳过去 | 最安全，最打断，无法无人值守 |

**倾向 B，加三条硬限制**。

1. **默认关闭**，必须显式开启，且只在插件自己发起的任务内有效；
2. 白名单**不含** `bash`、`pwsh` 这类参数不可见的工具，除非用户在本任务里逐项勾选；
3. 每次自动放行写 `_ledger.json`（时间、agent、toolName、callId），窗口关闭时给用户一条汇总，说明哪些是自动过的、哪些仍需人工。

A 作为逃生口保留，C 作为兜底。

**待定**。窗口用"任务开始/结束"自动开关，还是每个任务显式声明时长？后者更可控，但要改调用约定。

## 4 插件拉起的会话显示为「未命名对话」

状态：**待修**（缺陷，已在实盘出现）

**现象**。侧栏里本插件创建的会话显示为「未命名对话」，一次性出现多个。同类现象也影响了插件自己，候选列表里只能显示 `(未命名会话)` 或 `agent-<id 尾号>`。

**根因**（已核实宿主契约）。标题由 `sessionTitle` 服务生成，自动模式的取值是 `'first-prompt' | 'all-prompts'`，输入只来自**用户消息**。本插件建会话时不写用户消息，旧版信箱投递走的是 `schedule` 卡片，不算用户消息，所以标题生成器从来没有可用的输入，fallback 也不会跑。

**2026-11-17 更新**：通知改走 `sessionController.prompt` 之后，目标会话确实会收到一条用户消息，标题生成器这时有输入了。但这只解决「收到过通知的会话」，刚建还没收到信的会话仍然是未命名，所以建会话后 `rename` 的方案仍然要做，只是紧迫性下降。

**宿主提供的修法**。

```
sessionTitle.rename(session, title)   // 显式设定，会 pin 住标题
sessionTitle.refresh(session, signal) // 重试 provider，无 provider 时生成内置 fallback
```

**方案**。建会话成功后按任务语义直接 `rename`：标题取「项目名 · 预设」或调用方给的 `title`，拿不到就退回 `refresh`。`rename` 只在会话 live 时可调用，建完立刻调用窗口是够的。

**要接受的代价**。`rename` 会 **pin** 标题，之后该会话收到第一条用户消息也不会再自动生成或改名。对本插件创建的会话这是期望行为，因为名字来自建会话时声明的用途；但要在文档里写清楚，避免用户以为是 bug。

**待定**。默认 pin，还是先 `refresh` 让宿主编一个、只在拿不到时 `rename`？前者可预测，后者更省事但可能生成与用途无关的标题。

## 5 待办信件在目标重新活跃后不会自动重推

状态：**已修**（v0.2 信使通道，2026-11-17；规格见 `docs/superpowers/specs/2026-11-17-courier-backpressure-design.md`）

**现象**。一封跨工作区信发往另一个工作区的 `lead`，`toPath` 是 `P>B`：卡片确实进了对方收件箱（`P`），但对方在 5 分钟内没有起任何一步，回执标记没进过 step，于是超时转 `B` 待办。之后对方再活跃也不会收到这次提醒，因为哨兵在信件转 `blocked` 时就退出了。

**影响**。目标会话只是"暂时没被唤醒"，并没有出错，却要人工去捞。跨团队协作里这种空转很常见。

**方案候选**。

| 方案 | 做法 | 代价 |
|---|---|---|
| A 待办也留哨兵 | `blocked` 信件保留 idle 边触发器，目标下次空闲时补推一条索引 | 待办期间会反复触发，需要限次（例如最多 3 次）与退避 |
| B 归档时补推 | 检测到目标从 `archived` 恢复或被重新加载时，补推一次 | 覆盖面窄，只解决归档场景 |
| C 只在首次超时时补推一次 | 转待办的同一时刻再推一条"你有封待办信" | 最省，仍可能错过 |

**实修：走 A，但不靠「次数 + 退避」，改成「状态驱动 + 通道串行」。**

- 待办信进 `_courier.json` 持有队列，等目标回到 `idle` 才重新排队；空闲时先报数（「你有 N 封没处理」），再一封一封递，下一封以「上一封被消费」为闸门，不看秒数。
- 每封信单次投递失败重试 3 次即 `dropped`；同一会话未消费的卡在途最多 1 张，重复提醒从制度上不存在。
- 静置超过 `staleAfterMs`（默认 30 分钟）仍没人动，才允许补一次催收，单封上限 2 次。
- 发送侧加背压：同一对 (from,to) 未结案的信最多 1 封，`S-ACK` / `S-TODO-NOTICE` 豁免。
- 提醒拆两形态：收信方拿逐封催收，发信方拿聚合摘要，摘要里明说「不是对方不理你」，避免决策方把待办读成沉默而停等。

**旧的待定已由实现回答**：不再每次 idle 边重推，而是「在途 ≤ 1 + 看门狗单次」，所以「补推算不算骚扰」这个问题不再是权衡，而是有上限的兜底。

## 6 工作区与会话的清理：自动提议、人工书面确认、可撤回

状态：**功能性待办**（新能力，需求已明确）

**需求**。Agent 探索时经常建出用不上的工作区与会话，例如为了对比方案起了调研员，讨论完发现不需要了。现在只能由人手动收拾。倾向是自动清理，但不能让 Agent 自己决定删东西。

**宿主已给的原语**（逐条核实过契约，不是推测）。

| 方法 | 实际行为 |
|---|---|
| `workspaceRegistry.delete(id)` | **只删登记，保留目录与全部会话日志**。顺序表先更新，写失败会回滚；未知 id 是幂等空操作 |
| `workspaceRegistry.archiveSession(sessionId, {stopActivity?})` | durable 归档。不带 `stopActivity` 时会话必须不在活动状态，否则抛 `WorkspaceActiveSessionError`；带则先写归档再请求停止，唤醒会被 `agent/pre-step` 的归档闸门挡住 |
| `workspaceRegistry.unarchiveSession(sessionId)` | 撤销归档，回到原位置，不校验会话是否还在 |
| `workspaceRegistry.create(path, title?)` | 按目录重新登记，同路径重复调用返回已有实体 |

**撤回这件事比预想的简单**。`delete` 本来就不动磁盘，撤销就是把同一个路径 `create` 回来；会话侧有 `unarchiveSession`。所以整套清理**天然可逆**，不需要额外的快照机制。

顺带纠正一个记错的点：`dsh-rewind-lite` 做的是**会话内回退**（撤回对话到某条更早的用户消息）加文件还原，跟工作区登记、会话归档不是一回事，这里用不上它。

**两阶段确认设计**。

```
第一阶段  session_cleanup propose
          参数：workspace 路径或 id、要归档的会话 id 列表
          动作：不执行任何变更，只返回一条待确认文本与一个 intentId
                文本形如「确认对 <项目> 工作区执行注销登记、并归档 3 个会话？同意请回复：我同意」
                意图有效期 10 分钟，写进 .dsh-mail/_cleanup.json

第二阶段  session_cleanup confirm
          参数：intentId + phrase
          动作：校验三件事后才执行
                1.intentId 未过期、未被使用
                2.phrase 与要求文本逐字相等
                3.当前会话本轮的用户消息里确实出现过该短语
```

第 3 条是关键：`agent/pre-step` 拿得到本轮消息，只在 `user/message` 里出现短语才算数，Agent 从工具参数里塞一句不算。这样"必须人正式同意"才落得下去。

执行后把 working 内容写 `_ledger.json`（谁提议、谁确认、删了哪个工作区登记、归档了哪些会话、可撤销的方式），便于事后追溯与恢复。

**自动清理的边界**。

- 只**自动提议**，永不自动执行。提议由触发条件驱动：任务专用通道 retirement 后仍有成员会话闲置、会话工作区目录已不存在、同项目重复建了多个工作区且只有一个有信件往来。
- 提议通过一条通知消息（`sessionController.prompt`）投给发起方会话，而不是直接弹窗；人若不理，10 分钟后意图自然过期，不做任何变更。
- 有未读信、有待办信、或会话仍被 pin 的，一律不建议清理。

**风险**。

- `delete` 是登记层删除，界面上的会话会失联；如果人类误同意，恢复靠 `create(path)` 重新登记，但**会话与工作区的归属关系会丢**（`sessionIds` 由 cwd 索引重算，重算结果取决于会话日志仍在不在）。
- `archiveSession` 带 `stopActivity` 会真的中断正在跑的任务，必须单独再确认一次，不能与普通归档混在同一步。
