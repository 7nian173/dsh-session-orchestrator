## 1 好友表按名字做全局键，跨工作区同名会话互相覆盖

状态：**待修**（缺陷，已在实盘触发）

**现象**。同一个 DSH 实例里，不同工作区的会话在 `friends.json` 里以名字为唯一键。两个工作区各有一个叫 `lead` 的会话时，后注册的把前一个覆盖掉，前一个再发信就报 `SENDER_NOT_REGISTERED`。

实测：`E:/AI Projects/Super-agent` 的 `lead` 覆盖掉本机 `D:/dshdata/本地` 的 `lead`，后者发信失败，只好改名成 `plugin-author` 才恢复。

**影响**。多项目共用一个实例时必然踩，且失败发生在发信那一刻，看起来像插件坏了。

**方案候选**。

| 方案 | 做法 | 代价 |
|---|---|---|
| A 名字加工作区前缀 | 注册时默认 `工作区简称-名字` | 破坏现有名字的可读性，迁移要处理已有条目 |
| B 键改成 `(工作区, 名字)` | 表结构升 v2，查找按调用方工作区 | 要写迁移；跨工作区查找规则要重新定义 |
| C 冲突时自动加后缀 | 撞名就 `lead-2` | 治标，用户记不住到底是哪个 |

倾向 B，配一条迁移：旧表读入时按 `sessionId` 反查 cwd 补齐工作区字段。

## 2 自动化流程被人工审批打断

状态：**方案待定**（设计改进）

**现象**。插件驱动的自动化部署走到需要授权的工具时，必须有人点同意，流程停在那里等。对"让 agent 自己跑完"的场景这是硬阻断。

**宿主提供的接口**（已核实契约）。

```
approval/request  waterfall  (req, next) => Promise<ApprovalOutcome>
req: { agent, toolName, callId?, reason?, displayReason?, signal? }
ApprovalOutcome: 'allowed-once' | 'rejected' | 'cancelled' | 'unavailable'
```

事件是 scope-filtered 的，agent 级别的监听只收该 agent 的请求。插件返回一个 outcome 即claim 该请求，返回 `next()` 则交给下一个应答者。

**一个关键限制**。`req` 里**没有工具参数**，只有 `toolName`。所以自动放行只能按"哪个工具"判断，判断不了"哪条命令"。放行 `bash` 就等于在该窗口内放行任意 bash 命令。

**方案候选**。

| 方案 | 做法 | 风险 |
|---|---|---|
| A 一次性授权 | 用户把权限档位调高，整段任务不再逐次询问 | 粗粒度，覆盖全程，无法追责到具体调用 |
| B 插件端自动审核窗口 | 插件订阅 `approval/request`，窗口期内只对白名单工具回 `allowed-once`，其余交给人；窗口随任务自动开关，每次放行写留痕 | 本质是绕过人工闸门，白名单错一次就是事故 |
| C 跳转让用户手点 | 维持现状，遇到授权就跳过去 | 最安全，最打断，无法无人值守 |

**倾向 B，加三条硬限制**。

1. **默认关闭**，必须显式开启，且只在插件自己发起的任务内有效；
2. 白名单**不含** `bash`、`pwsh` 这类参数不可见的工具，除非用户在本任务里逐项勾选；
3. 每次自动放行写 `_ledger.json`（时间、agent、toolName、callId），窗口关闭时给用户一条汇总，说明哪些是自动过的、哪些仍需人工。

A 作为逃生口保留，C 作为兜底。

**待定**。窗口用"任务开始/结束"自动开关，还是每个任务显式声明时长？后者更可控，但要改调用约定。

## 4 插件拉起的会话显示为「未命名对话」

状态：**待修**（缺陷，已在实盘出现）

**现象**。侧栏里本插件创建的会话显示为「未命名对话」，一次性出现多个。同类现象也影响了插件自己，候选列表里只能显示 `(未命名会话)` 或 `agent-<id 尾号>`。

**根因**（已核实宿主契约）。标题由 `sessionTitle` 服务生成，自动模式的取值是 `'first-prompt' | 'all-prompts'`，输入只来自**用户消息**。本插件建会话时不写用户消息，信箱投递走的是 `schedule` 卡片，不算用户消息，所以标题生成器从来没有可用的输入，fallback 也不会跑。

**宿主提供的修法**。

```
sessionTitle.rename(session, title)   // 显式设定，会 pin 住标题
sessionTitle.refresh(session, signal) // 重试 provider，无 provider 时生成内置 fallback
```

**方案**。建会话成功后按任务语义直接 `rename`：标题取「项目名 · 预设」或调用方给的 `title`，拿不到就退回 `refresh`。`rename` 只在会话 live 时可调用，建完立刻调用窗口是够的。

**要接受的代价**。`rename` 会 **pin** 标题，之后该会话收到第一条用户消息也不会再自动生成或改名。对本插件创建的会话这是期望行为，因为名字来自建会话时声明的用途；但要在文档里写清楚，避免用户以为是 bug。

**待定**。默认 pin，还是先 `refresh` 让宿主编一个、只在拿不到时 `rename`？前者可预测，后者更省事但可能生成与用途无关的标题。

## 5 待办信件在目标重新活跃后不会自动重推

状态：**方案待定**（设计缺口，今日实盘撞到）

**现象**。M-20261117-0022 发往另一个工作区的 `lead`，`toPath` 是 `P>B`：卡片确实进了对方收件箱（`P`），但对方在 5 分钟内没有起任何一步，回执标记没进过 step，于是超时转 `B` 待办。之后对方再活跃也不会收到这次提醒，因为哨兵在信件转 `blocked` 时就退出了。

**影响**。目标会话只是"暂时没被唤醒"，并没有出错，却要人工去捞。跨团队协作里这种空转很常见。

**方案候选**。

| 方案 | 做法 | 代价 |
|---|---|---|
| A 待办也留哨兵 | `blocked` 信件保留 idle 边触发器，目标下次空闲时补推一条索引 | 待办期间会反复触发，需要限次（例如最多 3 次）与退避 |
| B 归档时补推 | 检测到目标从 `archived` 恢复或被重新加载时，补推一次 | 覆盖面窄，只解决归档场景 |
| C 只在首次超时时补推一次 | 转待办的同一时刻再推一条"你有封待办信" | 最省，仍可能错过 |

倾向 A 加限次与退避：`blocked` 后保留触发器，目标每次转入 idle 补推一次索引，最多 3 次，之后彻底静默，状态与留痕全部照写。

**待定**。补推算不算"骚扰"？对外部团队来说，一封信被推 3 次比漏掉更可接受。
